# 会议操作与状态语义

## 一次业务调用如何走到结果

ADP 提取意图后，由可信调用层生成可在该次重试中稳定使用的 `operation_id`；MCP 验证动态签名身份和正式 Schema；业务服务查询/写入本地台账并执行会畅资源与归属判断。**真正的 COMMITTED 需要会畅写接口确认并回读完整的原会议详情**，仅 HTTP 200 或查询到空闲不能证明创建成功。

默认五个 MCP Tool：`ping_meeting_server`（免认证握手）、`whoami_probe`（签名身份探针）、`submit_meeting_request`（CREATE/CHECK/UPDATE）、`continue_meeting_request`（补参/候选/取消）、`get_meeting_operation`（只查本地记录）。详见 [src/meeting_reservation/mcp_server.py](../../src/meeting_reservation/mcp_server.py)。可选临时 `identity_binding_probe` 只测试参数传递，不属于会议业务契约；见 [docs/integrations/02_腾讯ADP与MCP接入.md](../integrations/02_腾讯ADP与MCP接入.md)。

## 三种业务意图

| 意图 | 实际动作 | 关键失败或限制 |
| --- | --- | --- |
| CREATE | 校验必要字段 → 本人会议重叠 → 会畅容量/虚拟资源 → 受开关保护的提交 → 详情回读 | `NEED_INPUT`、`CONFLICT`、`DENIED`、`UNKNOWN` |
| CHECK | 校验起止时间 → 本人会议重叠 → 会畅资源可用性 | `AVAILABLE` 不等于锁定资源；**不写会畅**，但仍可能记录 SQLite 操作/pending |
| UPDATE | 定位原会议 → 所有权和未开始状态 → 统一差量修改 → 资源检查（需要时）→ 写后回读 | 多候选 `NEED_SELECTION`；不能修改他人或已开始会议 |

对不支持的 OTHER、实体 A301、参会者邀请/描述写入，必须明确报错而不是无声丢弃。状态处理和 Provider 调用见 [src/meeting_reservation/service.py](../../src/meeting_reservation/service.py)。

## 状态如何由调用方处理

| `meeting.result.v1` 状态 | 合理的 ADP/调用方动作 |
| --- | --- |
| `COMMITTED` | 仅展示 `confirmed_meeting` 的真实确认摘要 |
| `AVAILABLE` / `UNAVAILABLE` | 展示当前只读检查结果，不承诺预订成功 |
| `NEED_INPUT` / `NEED_SELECTION` | 保留 `pending_request_id`、`pending_revision`、`expires_at`，向同一用户补问或展示候选 |
| `CONFLICT` | 说明冲突，使用有效 pending 重新补充时段或选择；不能直接认定有可用替代 |
| `IN_PROGRESS` | 查询**同一个** `operation_id`，不能换号重建 |
| `UNKNOWN` | 查询原本地操作、核实会畅后台；禁止自动重复写入 |
| `DENIED` / `INVALID` / `NOT_FOUND` / `FAILED` / `EXPIRED` | 显示安全错误、要求正确输入或联系运维；不能当成功 |
| `CANCELLED` | 只取消本地 pending，**不取消已创建会议** |

机器上实际允许的字段和结果条件由 [src/meeting_reservation/schemas/meeting-result.v1.schema.json](../../src/meeting_reservation/schemas/meeting-result.v1.schema.json) 定义；不在文档重复完整状态条件判断。

## 为什么需要 operation_id 与 pending 两套 ID

- `operation_id` 绑定一次不可混用的身份与请求摘要；同 ID 的重复请求拿旧结果，不再发起新会畅写操作。对本地记录的未知状态只能查询，**不能自动查询会畅并改写状态**。
- `pending_request_id` 标记还在等待用户回答的那一次申请；它要求当前 Actor、revision、有效期与未消费状态正确。继续处理使用**新的** `operation_id`，原 pending ID/revision。
- `SUPPLY_FIELDS` 的写前业务校验错误允许保留原申请以纠正，原错误 operation ID 的结果仍可查询；真正写后未知不能借此重新尝试。
- 会畅 `202`/`205` 的明确冲突可产生 `CONFLICT`，网络断连、未知写响应、确认字段损坏或写后回读失败进入 `UNKNOWN`。**创建前检查可用不是原子预留**，本地 SQLite 也不能保证会畅的 exactly-once。

本地台账机制见 [docs/architecture/02_身份认证与操作状态.md](../architecture/02_身份认证与操作状态.md)，异常操作和安全恢复见 [docs/operations/03_故障排查与恢复.md](../operations/03_故障排查与恢复.md)。真实 ADP 与会畅验证仍是 [docs/testing/01_测试与联调验收.md](../testing/01_测试与联调验收.md) 的外部门禁。
