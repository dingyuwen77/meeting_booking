# 部署配置与运行维护

## 运行模型与为什么要保守部署

当前服务使用 **单实例 Python MCP Server + SQLite 持久台账 + 会畅外部 OpenAPI**。SQLite 的操作号和 pending 防重复保护依赖同一份持久化数据；不能复制成多个各持本地数据库的副本后仍声称具备原有幂等保证。本仓库没有分布式协调、版本化数据库 Migration、自动部署或生产可用性证据。

已有 [Dockerfile](../../Dockerfile)、[compose.yaml](../../compose.yaml)：Docker 基础镜像 Python 3.11-slim；Compose 指定 `linux/arm64`，容器内部监听 `0.0.0.0:4561`，默认只映射宿主回环 `127.0.0.1:4561`。SQLite 数据放在命名卷 `meeting_data` 中的 `/app/data`，不是容器临时可写层。**目标服务器不是 ARM64 时，需先核对架构与部署变更，不能假定模板直接原生运行。**

## 1. 配置与首次部署

1. 在目标宿主准备 Python/Docker 环境并确认其 CPU 架构、磁盘备份能力、端口和访问控制。
2. 参考 [.env.example](../../.env.example) 在部署宿主提供本地 `.env`（或受控 Secret 注入方案）。Compose 的 `env_file` 加载它；独立 Python 进程**不会自动读取**该文件。
3. 设置可信企业、签名密钥与必要的会畅站点参数；所有敏感值保持仓库外。保留 `MEETING_WRITE_ENABLED=false`，没有真实联调授权前不要启用。
4. 检查 Compose 展开结果，再按目标平台构建和启动；下面命令仅为文档化的仓库入口，本次文档治理不声称已在目标服务器实际执行。

```bash
docker compose config --no-env-resolution --quiet
docker build --platform linux/arm64 -t meeting-booking:local .
docker compose up -d
docker compose ps
docker compose logs --tail 100
```

在容器内服务监听 `0.0.0.0` 只意味着 Docker 网络可访问，不意味着允许公开给不可信客户端。Compose 当前只绑定宿主回环；要从云端 ADP 连接，必须通过**受控 HTTPS 代理/可信调用层**提供地址，并确保业务 Tool 的每次调用仍收到合法的动态签名身份。

## 2. MCP Host/Origin 与网关

MCP SDK 自带 Host/Origin 防护。反向代理配置不正确可能导致 `421 Invalid Host header`；应同时核对 SDK 当前允许的 Host、代理到回环端口的 upstream Host，以及客户端的 Origin，不要关闭 Host 检查或设置无限制通配符。参考 [MCP Python SDK 部署说明](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/run/deploy.md) 并与实际安装版本复核。

TLS 终止、来源认证/准入及每轮真实成员身份由可信网关保障；本服务的 HMAC 只验证已签发声明，不代替对企微原始事件的认证。真实动态 Header 转发必须在 ADP 租户里单独核验，不能靠静态 Header 假冒全体用户。

## 3. 状态文件、备份和恢复

[源码：src/meeting_reservation/state.py](../../src/meeting_reservation/state.py) 使用 SQLite WAL 模式和启动建表；Compose 默认文件为 `/app/data/meeting_booking.sqlite3`。存储中可能包含企业成员标识、会议意图与结果，备份应加密/限制访问、标明时间与运行版本。**运行中不要只拷贝主 `.sqlite3` 文件并认定为一致性备份**，WAL 可能仍有未 checkpoint 的提交。

对运行中的数据库可使用 Python 标准库 `sqlite3.Connection.backup()` 生成一致性快照；下例仅示意在部署环境已经授权、路径及剩余空间已核对时运行（不会写会畅）：

```python
import sqlite3

source = sqlite3.connect("/app/data/meeting_booking.sqlite3")
backup = sqlite3.connect("/app/data/meeting_booking-backup.sqlite3")
try:
    source.backup(backup)
finally:
    backup.close()
    source.close()
```

在容器环境执行这段代码需使用受控的 `docker compose exec` 或等价维护方式；**备份文件仍位于命名卷内，必须另行复制到独立的安全存储，并验证能重新打开**。用只读连接执行 `PRAGMA integrity_check` 核验备份完整性，并定期演练恢复。不能把同一个命名卷既当工作数据又当唯一备份。

恢复到旧快照前应先停止服务、保留当前数据库和可能的 WAL/SHM、核实备份来源及操作记录、取得负责人的恢复授权。恢复会丢失备份时间点之后的本地操作状态，但可能不会撤销相应的**远端会畅会议**；后续 UNKNOWN/重复写入风险必须人工核对，不能自动重放。

## 4. 停止、升级与回滚

```bash
docker compose logs --tail 100
docker compose down
# 不加 -v：保留 meeting_data 命名卷
```

升级/回滚前先备份台账、固定镜像/依赖与配置 revision，验证当前待处理操作。`docker compose down -v` 会删除命名卷，**不能**作为普通停机或回滚命令。当前只有首次运行的建表逻辑；没有版本化 Migration，数据结构变化必须另行设计兼容及回滚测试。

回滚服务代码和关闭 `MEETING_WRITE_ENABLED` 只是减少**后续写入**；不能取消已经在会畅创建/修改的会议，也不能替代 UNKNOWN 的远端人工确认。具体现象、恢复检查与安全限制在 [docs/operations/03_故障排查与恢复.md](03_故障排查与恢复.md)。

## 5. 生产写入启用前的硬门禁

必须分别证明：供应商原 API 文档与实际站点权限/容量；两名企微真实成员身份及动态签名；受控会畅创建/修改/回读；ADP 工具和多轮结果消费；网关可达性与持久化恢复；目标环境发布授权。证据要求在 [docs/testing/01_测试与联调验收.md](../testing/01_测试与联调验收.md)。**部署成功、MCP ping 通过或代码已合并，都不授权开启真实写入。**
