# 故障排查与恢复

## 为什么先定位阶段，再决定是否重试

同样是“会议没有返回成功”，可能是参数不合法、签名失效、会畅明确拒绝，也可能是会畅已经创建成功但响应丢失。只有最后一类涉及**重复创建的不可逆风险**。因此先判断失败发生在 **MCP/身份 → Schema/业务 → SQLite → 会畅读取 → 会畅写入 → 写后回读** 哪一层，再决定补参、重试只读请求或人工核实。

当前没有自动远端对账、自动修复 UNKNOWN、第三方 exactly-once 或已创建会议取消机制。恢复操作只适用于有权限的管理员，严禁将真实密钥、签名 Header、Token、会议密码或完整原始请求写入工单和日志。

## 1. 常见现象与第一检查点

| 现象 | 应先检查的真实边界 | 安全动作 |
| --- | --- | --- |
| Python 命令找不到包或启动失败 | 虚拟环境、[pyproject.toml](../../pyproject.toml)、启动异常 | 按本地安装文档重装；不改源码的导入路径掩盖问题 |
| MCP ping 不通 | 监听 `MEETING_MCP_HOST/PORT`、容器/代理、网络 | 先 MCP initialize/tools/list，再 ping；不要发送会畅写请求 |
| `421 Invalid Host header` | 代理 upstream Host 与 MCP SDK Host/Origin 规则 | 检查可信代理配置，不关闭 Host/Origin 防护 |
| `whoami_probe` 或业务工具拒绝身份 | `X-Meeting-Actor`/签名、CorpID、90 秒窗口、共享密钥 | 由可信上游重新签发身份声明，不接受模型自报 UserID |
| `DENIED` + `WRITE_DISABLED` | `MEETING_WRITE_ENABLED` 默认关闭 | 不能仅为调试把生产写开关打开 |
| `INVALID` / `NEED_INPUT` | Schema、标题/时区/时长、缺字段、业务限制 | 调整原意图或按 pending 补参；不生成冒用身份 |
| `NEED_SELECTION` / `CONFLICT` | 已保存候选、本人时段冲突、虚拟资源 | 保留 pending ID/revision，由同一用户选择或补充时段 |
| `FAILED` 或会畅读取错误 | API 配置、Token、POST/GET、供应商状态码 | 核实是只读或明确失败；对未知写入绝不盲重试 |
| `IN_PROGRESS` | 本地 operation 未存最终结果 | 查询相同 `operation_id`，不能换号再提交 |
| `UNKNOWN` | 写入响应/回读失败，或本地操作超过约 30 秒仍未终结 | 停止自动写入重试，执行下面的远端核实 |
| 重启后丢记录/数据库锁异常 | SQLite 文件、挂载卷、权限、WAL/恢复 | 暂停相关写入，验证数据卷及一致性备份，保留现场 |
| ADP 无法处理 `structuredContent` 或跨轮失败 | 工具 Schema、调用层保存的 ID、动态 Header 传递 | 分离 ADP 与 MCP 测试，不能从本地 Mock 推断租户行为 |

项目入口见 [docs/operations/01_本地运行与调试.md](01_本地运行与调试.md)，实际配置见 [.env.example](../../.env.example)。别把 HTTP 200 当作会畅 `status==100`。

## 2. UNKNOWN 的受控处理流程

1. **记录原始业务操作标识** `operation_id`、操作者范围、目标会议信息、请求时段与脱敏错误类别；不得在工单中记录明文 APIKey/Token/签名或入会密码。
2. 用同一已验证身份调用 `get_meeting_operation` 查询**本地**结果：若仍是 `IN_PROGRESS`/`UNKNOWN`，不能解释为会畅一定失败；这个工具**不会请求会畅查重**。
3. 由拥有权限的人在会畅后台或经批准的只读接口，按相同成员、会议名称、时间范围和实际会议 ID 核对**是否已经发生创建或修改**。记录脱敏的会议事实、核对时间、责任人和依据。
4. 如发现会议已存在，避免任何第二次提交；根据真实回读/人工确认执行受控后续处理。本仓库目前没有“人工确认后把 UNKNOWN 改成 COMMITTED”的管理 API，不允许直接改 SQLite 伪造结果。
5. 如果仍无法确认，保持 UNKNOWN 并暂停相同业务意图的自动重复写入；只有完整证据和单独授权的恢复方案才能进一步操作。

**不要用新 operation_id 试一次**：在远端创建成功但客户端没拿到回执的情况下，会导致第二场会议。也不要误以为关闭服务或回滚代码可撤销远端写入。

## 3. pending 补参失败如何处理

对 `NEED_INPUT`/`NEED_SELECTION`/`CONFLICT`，保存真实的 `pending_request_id`、`pending_revision`、有效期与原 UserID；继续处理使用**新的** operation ID。若只是写入前的补参业务校验失败，原 pending 在业务层受控释放后可能仍可纠正；已过期、已消费或跨用户不可复用。

`CANCEL` **只取消待处理申请，不取消已创建会议**。当前不提供已创建会议取消 API。实现见 [src/meeting_reservation/service.py](../../src/meeting_reservation/service.py)、[src/meeting_reservation/state.py](../../src/meeting_reservation/state.py)；结果字段见 [docs/contracts/02_会议操作与状态语义.md](../contracts/02_会议操作与状态语义.md)。

## 4. SQLite、备份与回滚的故障边界

- 首先确认 `MEETING_DB_PATH` 实际路径/权限与 Compose 的 `meeting_data` 命名卷；数据在容器临时文件系统中没有可靠持久化保证。
- SQLite 采用 WAL 模式。**运行中仅复制主 DB 文件可能缺失尚在 WAL 的事务**；需使用 `sqlite3.Connection.backup()` 一致性快照，验证可重新打开并执行 `PRAGMA integrity_check`。完整部署方法见 [docs/operations/02_部署配置与运行维护.md](02_部署配置与运行维护.md)。
- 需要恢复数据时先维护停机、保全现状及备份、校验快照来源与对应服务 revision，避免清理 WAL 或覆盖尚未核实的 operation/pending 记录。
- 恢复旧台账可能让本地操作记录比会畅事实更旧，**不能因为本地查不到就认为会畅没创建过**。人工核实之后才决定是否恢复可写服务。
- 回滚代码、关闭写入、停机都不能回滚会畅会议事实。无现成独立 Migration 工具，结构变化不适合直接在现场边运行边恢复。

## 5. 证明哪一层已恢复

MCP 连接恢复应有 `ping_meeting_server` 证据；身份恢复应有受控 `whoami_probe`；台账恢复需实际查询既有操作且数据库完整性通过；会畅写操作恢复必须取得真实站点回读及业务方确认；ADP/企微恢复需真实租户端到端验证。**只通过本地 Fake/SDK 测试，不能宣称外部会畅或企微恢复。** 验收入口见 [docs/testing/01_测试与联调验收.md](../testing/01_测试与联调验收.md)。
