# 系统架构与业务边界

## 为什么需要单独的会议执行服务

企业微信里用户可以说“明天的评审会延后半小时”，但自然语言既不能证明操作者身份，也不能证明会议真实可用或更新成功。ADP 负责理解意图；本仓库中的 MCP 服务负责**确定性校验与执行**；会畅智云是会议详情和实际提交结果的权威来源。这样可以避免由模型自行判断权限、占用和提交成功。

当前代码已实现 MCP → 服务 → 会畅适配与 SQLite 这一段；企业微信网关、腾讯 ADP 在线应用和真实会畅站点的联通**尚待环境验收**。

## 端到端目标链路与当前仓库边界

```text
[仓库外，待联调] 企业微信成员 / 消息
    → 可信渠道网关核验成员身份
    → 腾讯 ADP 理解 CREATE / CHECK / UPDATE / OTHER 和多轮交互
    → 可信调用层提供稳定 operation_id、每轮动态签名身份
[本仓库] MCP Streamable HTTP tools/call
    → 验证 X-Meeting-Actor / X-Meeting-Signature
    → 从五份 Schema 校验 request / continue / operation-query
    → MeetingService：补参、归属、资源检查、写入开关
    ↔ SQLite：operation_id 幂等与 pending 状态
    → BizVideoProvider：会畅 HTTP / GMT / Token
    → 会畅 OpenAPI：查询 / 提交 / 详情回读
    → 业务结果（有条件 COMMITTED，否则相应状态）
[仓库外] ADP 将结构化结果转为用户可见答复
```

这个图是**目标完整链路**，不是声称所有外部组件已打通。本仓库没有普通 REST 会议 API；接入请使用 MCP 客户端和 SDK 约定的 `initialize`、`tools/list`、`tools/call`。

## 谁负责什么

| 边界 | 真实职责 | 不负责 |
| --- | --- | --- |
| 企业微信/可信网关（仓库外） | 确认真实成员，动态签发短时声明，维持会话关联 | 不由模型文本替代验签 |
| 腾讯 ADP（仓库外） | 意图解析、提问、候选展示、工具编排 | 不自行裁定会畅是否已提交 |
| MCP 协议层 | 工具注册、Schema 投影、请求 Header 身份获取 | 不信任请求 JSON 中自报身份 |
| 业务服务 | 时段与资格判断、CREATE/CHECK/UPDATE、pending、幂等 | 不把“检查可用”当已提交 |
| SQLite 状态台账 | 本地操作结果/待处理请求持久化 | 不提供跨系统原子事务或自动对账 |
| 会畅 Provider | 端点和格式适配、远端状态检查、详情回读 | 不将供应商数据格式公开为 MCP Contract |

代码 Owner 见 [docs/architecture/03_代码结构与调用链导航.md](03_代码结构与调用链导航.md)。

## 实现能力与刻意不支持的范围

- **视频会议 != 实体办公室会议室**：会畅 `roomId` 是虚拟会议资源，只有 `bizvideo-room:<roomId>` 可直连；A301/A302 等实体地点没有映射事实，不可推断已占用或可预约。
- `CREATE` 在允许真实写入时，先查本人冲突/资源，再请求会畅创建，最终以写后详情回读确定状态。
- `CHECK` 不调用会畅写接口；通过业务 Tool 调用仍可能写入本地操作台账或待补参记录。
- `UPDATE` 先读取原会议，校验归属与未开始状态，再执行统一变更（含时间平移、绝对时间、标题或虚拟资源）。
- 不自动邀请参会者、不写入会议描述、不取消已创建的会议；`CANCEL` 仅取消本地待处理申请。没有多 Provider 切换、分布式调度或实体会议室日历。

失败可能出现在调用方、MCP 验签、SQLite、供应商写入和写后确认不同位置。最关键的不变量是：**结果不明时不能用新操作号重复写入**。身份、幂等与状态机制见 [docs/architecture/02_身份认证与操作状态.md](02_身份认证与操作状态.md)，状态定义见 [docs/contracts/02_会议操作与状态语义.md](../contracts/02_会议操作与状态语义.md)。
