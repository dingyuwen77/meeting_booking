# 代码结构与调用链导航

## 为什么需要这份导航

本页回答：**要修改某个会议行为，从哪个模块进入、沿什么调用链跟踪、对应测试在哪里？** 架构决定与状态语义归其他专题解释；这里不复制 Schema、逐行源码或一套可漂移的 API 定义。

## 实际业务调用路径

```text
mcp_server.py：工具注册、MCP 连接、HTTP Header
  → identity.py：校验本次 Actor 身份
  → contract.py + schemas：解析、校验 JSON
  → service.py：执行 CREATE / CHECK / UPDATE、补参和结果构造
       ↔ state.py：SQLite operations、pending_requests
       → bizvideo.py：会畅账号模式 HTTP API
  → service.py：写后回读或 UNKNOWN 等业务结果
  → mcp_server.py：structuredContent
```

[源码：src/meeting_reservation/mcp_server.py](../../src/meeting_reservation/mcp_server.py) 是协议入口；使用官方 MCP SDK v2 Streamable HTTP，`stateless_http=True`、`json_response=True`，不是自定义 REST 服务。业务依赖惰性创建，SDK 生命周期末尾关闭 Provider 自己创建的 HTTP 客户端。

## 三条排查阅读路径

### CREATE / CHECK / UNKNOWN

1. 在 `mcp_server.py` 找 `submit_meeting_request`，理解传给业务层的 `request` 和可信 Header。
2. 在 `service.py` 找 `_run` 和 `_create_or_check`：前者管操作号及结果保存；后者管必填字段、会畅资源和本人时段冲突。CHECK 不写会畅，但仍会记录本地状态。
3. 在 `bizvideo.py` 找 `scheduled`、`availability`、`create`、`_request`；确认真正发出的 GET/POST、表单、Token、超时如何转为确定失败或未知。
4. 回到 `service.py` 的 `_complete` 看写后回读和 COMMITTED 条件；去 `state.py` 读操作号查询，理解为什么 UNKNOWN 不能盲重放。

### UPDATE 与待决策请求

- `service.py` 的 `_resolve_target` 从真实会议 ID/名称寻找目标；多候选生成 `NEED_SELECTION`。`_update` 校验所有权和状态、执行统一时间/字段修改；Provider 分为 `modify_simple` 与 `modify`。
- `continue_request` 根据 `SUPPLY_FIELDS`、`SELECT_OPTION` 或 `CANCEL` 继续；`state.py` 的 `read_pending`/`consume_pending`/`release_pending` 决定是否可补参纠错。
- 契约允许表达的字段不等于会畅 API 已实现；新增业务能力必须同时核验 Schema、业务执行、Provider、测试和消费方说明。

### 本地 CLI / MCP

- `python -m meeting_reservation validate-examples --dir examples` 只验证契约示例。
- `python -m meeting_reservation.mcp_server` 启动 Streamable HTTP 服务；以 MCP Client/Inspector 调用 `initialize`、`tools/list`、`tools/call`，不要当普通 REST JSON POST。
- `get_meeting_operation` 只查询本地 SQLite 记录，**不自动询问会畅实际结果**。需要核对远端时转运维流程。
