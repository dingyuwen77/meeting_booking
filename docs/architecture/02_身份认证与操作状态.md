# 身份认证与操作状态

## 为什么 UserID 原样复用仍然需要验签

会畅账号模式的 `userId` 使用已验证的企业微信成员 UserID，不另建一张用户 ID 对照表；但字符串 `user_id=张三` **不能证明**请求确实来自张三。当前 MCP 业务工具只从可信网关签名的 HTTP Header 读取身份，模型、昵称和普通 JSON 参数都不具备认证效力。

[源代码：src/meeting_reservation/identity.py](../../src/meeting_reservation/identity.py) 负责验证；[源代码：src/meeting_reservation/mcp_server.py](../../src/meeting_reservation/mcp_server.py) 在每次有身份要求的工具调用中获取 Actor。业务操作和本地台账使用 `corp_id:user_id` 作为隔离键。

### 已实现的签名格式

1. 可信网关验证原始成员事件后构造 JSON，**恰好包含** `corp_id`、`user_id`、`user_name`、`iat`；`iat` 为 Unix 秒整数。
2. JSON 压缩为 UTF-8，再做不带末尾 `=` 的 Base64URL 编码。
3. 对该编码文本使用共享 `MEETING_IDENTITY_SECRET` 做 HMAC-SHA256，得到 64 位十六进制签名。
4. 编码文本传 `X-Meeting-Actor`，签名传 `X-Meeting-Signature`。
5. 服务端校验密钥长度（至少 32 字符）、企业 ID、成员 ID 格式、名称、签名及 `iat` 与当前时间不超过 90 秒。

`ping_meeting_server` 不要求身份；`whoami_probe` 和三个业务工具要求有效身份。`sign_identity` 是供可信上游/隔离测试使用的辅助函数，**不应让 ADP 模型或浏览器掌握共享密钥**。

HMAC 证明签名来自密钥持有者，**不会**自行核验企微原始消息，也不防止在有效时间窗口内重放相同 Header。可信网关须核实消息来源并限制直接访问，线上实际链路需可信 TLS、密钥管理与时钟同步。若 ADP 不能每轮动态透传签名，必须在可信接入/代理层解决，而不是禁用验签。

## 两类本地状态不是一回事

| 数据 | 为什么需要 | 代码 Owner |
| --- | --- | --- |
| `operations` | 用稳定 `operation_id` 识别一次业务意图，防止同一请求重复创建会议；记录执行结果供查询 | [src/meeting_reservation/state.py](../../src/meeting_reservation/state.py) |
| `pending_requests` | 用户缺字段、需选择候选或发生冲突时保存原意图与选择状态，等待下一轮输入 | [src/meeting_reservation/state.py](../../src/meeting_reservation/state.py) |

- 新操作先在 SQLite 事务中记录 `operation_id`、操作者键与规范化请求摘要。相同 ID+用户+请求返回旧结果；同 ID 不同请求报 `IDEMPOTENCY_MISMATCH`；他人 ID 不可访问。
- 初始操作未完成时返回 `IN_PROGRESS`；**超过约 30 秒而仍无最终结果的记录，查询显示 `UNKNOWN`**。这只是本地超时归类，不是对会畅远端状态的新确认。
- `NEED_INPUT`、`NEED_SELECTION`、`CONFLICT` 建立具有持有人、revision 和约 30 分钟有效期的 pending。继续处理要提供原 ID、`expected_revision` 和**新** `operation_id`，先校验归属、是否已消费和有效期。
- 一次 pending 只能被成功消费一次。若仅是**写入前的业务补参校验失败**，业务层有受控释放路径允许同一持有人修正输入；如果远端结果可能不确定，则不得据此自动重新写入。

这些状态由 [src/meeting_reservation/service.py](../../src/meeting_reservation/service.py) 使用。五份 Schema 的字段形状与校验器分别在 [src/meeting_reservation/schemas/](../../src/meeting_reservation/schemas/) 和 [src/meeting_reservation/contract.py](../../src/meeting_reservation/contract.py)。

## 哪些保证不能从 SQLite 得出

当前使用单实例、本地持久 SQLite、启动建表和 WAL 模式；不使用内存数据库。SQLite 的事务保证本地操作号与 pending 消费的一部分并发约束，**不能让本地插入与会畅创建变成同一个原子事务**。本地崩溃、写入确认失败或会畅先提交后断连都可能留下 UNKNOWN。

`get_meeting_operation` 只读取本地记录，不会重新查询远端或自动清算未知操作。若需要外部核实，应先查询原操作，再在有权限的会畅控制台核对，避免换 operation_id 盲重试。
