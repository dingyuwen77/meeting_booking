# 身份认证与操作状态

## 1. 企微 UserID 原样复用

会畅账号模式 API 将 `userId` 定义为“客户系统用户唯一 ID”。本服务接收到已验证身份后，`BizVideoProvider` 原样传入 `Actor.user_id`，不生成第二套会畅用户 ID；`userName` 取成员当前可验证名称，首次在会畅存档后可能不随之后的变更更新。

这只是**身份映射**，不是认证。模型生成的 `user_id`、展示昵称、ADP 静态 Header 和会话文本都不能证明企微成员身份。

## 2. 可信网关签名要求

本仓库的验证机制是短时 HMAC-SHA256 身份声明。可信网关在核验企微原始事件身份后，生成严格 JSON 对象（字段 `corp_id`、`user_id`、`user_name`、`iat`），压缩 JSON 为 UTF-8 字节，再进行 **Base64URL（去 padding）** 编码。对完整编码字符串使用 `MEETING_IDENTITY_SECRET` 做 HMAC-SHA256，Hex 编码签名。将编码字符串放入 `X-Meeting-Actor`，签名放入 `X-Meeting-Signature`。

服务端每次 `tools/call` 独立检查签名、90 秒时间窗口、`MEETING_CORP_ID`、用户 ID 格式与必要字段。代码见 [src/meeting_reservation/identity.py](../../src/meeting_reservation/identity.py)。

**安全边界：** 签名密钥只能由可信网关和 MCP 服务端持有，不得传入 ADP Prompt、普通工具参数或前端；HTTPS 必须在可信网关到 MCP 的实际链路生效。签名数据可在短时间窗口内重放，因此网关还必须防止不受信调用方直连 MCP、避免凭据外泄；operation_id 不是身份凭据。

如果当前 ADP 部署模式不能把可信签名动态转发到 MCP，应由企业微信侧的可信服务/代理与 ADP 适配，不能为了联通而关闭验证。正式写入在此前保持关闭。

## 3. 幂等与待处理申请

[src/meeting_reservation/state.py](../../src/meeting_reservation/state.py) 在 SQLite 中保存两类数据：

- `operations`：由可信调用层提供稳定 `operation_id`。同一 ID + 同一用户 + 同一规范化请求返回同一结果；不同请求复用 ID 被拒绝。运行中与超时未知请求不会自动再次写入。
- `pending_requests`：`NEED_INPUT`、`NEED_SELECTION`、`CONFLICT` 保存原意图、选项、持有人、revision 与 30 分钟过期时间。补字段/选项必须由同一用户提交，成功消费后不能再次消费。

这不是分布式事务。远端写入成功、本地保存失败或回读失败时进入核实边界；在没有会畅原子幂等 API 的情况下不能宣称严格 exactly-once。

## 4. 部署限制

当前 SQLite 适用于**单主机、共享持久卷、保守单实例**；不能将临时容器文件系统视为可靠存储，不能部署为多个互不共享状态的副本。生产认证、并发、多进程/多机以及网关实际转发行为需依照 [docs/testing/01_测试与联调验收.md](../testing/01_测试与联调验收.md) 的外部验证门禁完成。
