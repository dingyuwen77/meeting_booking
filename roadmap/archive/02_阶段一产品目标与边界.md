# 01｜产品目标、责任边界与关键决策

> 读者：负责 ADP 编排、MCP 工具以及实际会议 API 对接的开发者。本篇回答“为什么这样分层”，不复制机器 Schema。

## 1. 业务目标

用户在企业微信说“明天下午两点订 A301 的评审会”，系统要完成一次**真实且可确认的会议创建**。如果资源被占用，则应让用户选择替代时间/会议室并在最终提交前重新校验。用户说“改会”时，应定位自己有权修改的原会议并在不影响其他字段的情况下提交差量更新。

V1 范围：CREATE 创建、UPDATE 修改、CHECK 只查询、OTHER 不执行会议写操作；参数追问、会议候选选择、会议室冲突、取消**待处理申请**、幂等和结果查询都属于 V1 必须闭环的支撑行为。

非目标：不自动取消/覆盖别人的会议，不自动调用会议录音/纪要，不开展多 Agent 自动协商。是否允许主动发起与会人日历邀请、是否给参会人发通知，取决于真实会议 Provider 的业务要求，不在当前资料中猜测。

## 2. 端到端真实职责

~~~text
企微用户（表达请求/做决策）
    ↓ 真实渠道身份
腾讯 ADP（识别意图、补参数、校验语义、工作流分支）
    ↓ meeting.intent.v1，经可信调用层组装 meeting.request.v1
固定 MCP Server（Schema校验、身份/授权、资源解析、状态管理、幂等）
    ↓ 不让模型做最终业务裁决
会议系统（会议/会议室/参会人真实数据、权限、最终提交）
    ↓ 真实执行状态和最终会议详情
MCP result → ADP 确定性分支 → 企业微信用户
~~~

**ADP 负责“用户想要什么”，MCP 负责“怎么安全地执行”，会议系统负责“最终发生了什么”。** MCP 不应在自己的缓存中维护第二份可能与会议日历不一致的真实会议占用数据。

## 3. 为什么必须有三类独立保护

- **业务正确性：** 先查询到空闲，不代表下一秒仍空闲。必须由权威数据源保证提交时的冲突保护；不同用户并发抢订不能双成功。
- **权限可信：** 模型输出“我是管理员”、群聊显示名、普通自填 user_id 都不是可信授权。MCP 必须验证调用来源和最终用户身份、会议归属及操作权限。
- **失败可恢复：** 创建 API 可能已经成功但响应超时。每次写操作需要稳定 operation_id 与可查询结果，不能通过重复调用“碰运气”。

## 4. 当前唯一事实源和协作界面

- JSON 的字段、必填、枚举、修改互斥条件：参见 [docs/archive/02_阶段一协议候选快照.md](../../docs/archive/02_阶段一协议候选快照.md)，机器定义位于 [src/meeting_reservation/schemas/meeting-intent.v1.schema.json](../../src/meeting_reservation/schemas/meeting-intent.v1.schema.json) 等 5 份 Schema。
- 后续会议业务 Provider 的接口定义，必须从其官方/内部接口文档、实际调用或测试数据取得；目前本地工程**没有**这份事实。
- ADP 配置/企业微信运行细节以当前腾讯 ADP 官方文档 + 真实租户验证为准，相关官方入口见 [roadmap/archive/04_阶段一MCP联通计划.md](04_阶段一MCP联通计划.md)。

## 5. 需由会议系统/业务 Owner 明确的上游决策

| 编号 | 决策/事实 | 建议基线 | 未定会阻塞什么 |
|---|---|---|---|
| B01 | 权威会议系统、测试 API、资源/用户 ID | 只复用已有事实源和业务 API | G1 正式冻结、G3 |
| B02 | 什么是“冲突” | 会议室时间重叠为硬冲突；与会人冲突由业务方定是否硬限制 | 创建、修改与替代方案 |
| B03 | 谁有创建/修改权 | 认证的本人或明确授权管理员，不信任模型角色 | 任何真实写入 |
| B04 | 缺少标题、会议室、结束时间时能否默认 | 默认只补问，不虚构；业务明确定义才可采用默认值 | 参数完整性 |
| B05 | 有冲突后允许哪些动作 | 换时间、换会议室、取消本次申请；不强占别人的会 | 冲突 UI 与状态机 |
| B06 | 修改已有会议的定位/并发规则 | 多候选先选择；按会议版本条件更新 | UPDATE |
| B07 | 参会人名单及通知语义 | 身份唯一解析；是否自动通知需与 Provider 确认 | CREATE/UPDATE |
| B08 | 生产时区、日历边界、缓冲时间 | 显式时区，采用真实组织规则而非模型猜测 | 冲突计算 |
| B09 | 真实写入时原子性/并发保护 | 必须由共享权威提交边界保障，MCP 本地锁不算证据 | G3、G6 |

**决策入口：** 由实现者调查会议 API/正式业务要求；只有现有材料不能得出的 B02/B04/B05/B07/B08 等业务语义交由 Owner 确认。决定后更新本篇的决策状态、相关测试，并检查是否改变契约。

## 6. 开发不变项

1. 当前 V1 只做明确请求的预约/修改/查询，不让 LLM 自由决定写入动作。
2. 自然语言中的会议室/姓名是查询线索，不是已核验的对象 ID。
3. CHECK 是只读，OTHER 不允许触发写工具。
4. 相对修改要先读原会议再计算目标时间；差量字段之外保持不变。
5. 群聊不能因为共享上下文而共享权限；不同用户不能继续他人的 pending 申请。
6. 生产数据、密钥、会议成员信息不得被普通调试日志或模型输出泄露。
7. 计划文档不能替代真实软件验证；证据层级见 [roadmap/archive/07_阶段一测试与交付计划.md](07_阶段一测试与交付计划.md)。
