# 会畅 MCP 改造与验收状态

## 1. 需求来源与范围

来源为用户已确认的系统改造方案及续接要求：企业微信 UserID 原样复用为会畅 userId；在现有 Python 契约工程内实现会畅账号模式 MCP 服务，全面治理文档，并通过 PR 合并远程 main。原任务明确豁免本次独立 AI Review；其余验证、权限与保护规则继续生效。

本仓库交付 MCP 服务、供应商适配、可信身份验证、业务状态、测试和维护文档。ADP 在线画布、企微网关与真实测试站点属于外部接入对象，当前没有其配置和可核验运行证据。**仓库合并验收与生产启用验收分别判定；未通过外部门禁不得宣称真实预订链路已交付。**

不包含实体办公室会议室日历、自动邀请、会议描述写入、已创建会议取消、录制纪要、多 Provider、分布式部署、Release 或生产部署。

## 2. 已确认的设计决定

- 复用五份 JSON Schema 与原 CLI；V1 仍为未冻结候选，统一 UPDATE，不恢复 SHIFT/PATCH。
- 企微 UserID 直接作为会畅 userId；HMAC 只验证可信网关的短时声明，不把模型输入当身份。
- 会畅 roomId 是虚拟资源；只接受 `bizvideo-room:<id>`，A301 等文本拒绝。容量取受控服务配置。
- 单实例 SQLite 保存操作号、请求摘要、pending 与结果。UNKNOWN 不自动重放；无自动跨系统原子事务或自动人工对账替代物。
- 写入默认关闭；会畅写后回读完整详情才可 COMMITTED，回读或确认失败进入 UNKNOWN。

方案比较：直接暴露供应商 API 无法收口身份、幂等与补参；重建多 Provider/分布式数据库会引入当前需求不需要的机制。因此保留原契约、增加业务服务与供应商边界。生产边界及调用链的解释 Owner 是 [docs/architecture/01_系统架构与业务边界.md](../docs/architecture/01_系统架构与业务边界.md)，不在路线图重复维护实现清单。

## 5. 兼容、迁移与回滚

本次在未冻结 V1 中增加 SUPPLY_FIELDS 和 COMMITTED 确认摘要；调用方应按当前 Schema 更新。增加 httpx 与 MCP v2 依赖，保留已有 jsonschema 约束与 CLI。SQLite 首次运行建表，没有已有生产数据迁移，不删除原台账。回滚时关闭写入、恢复旧服务并保留数据；回滚不会取消会畅已有会议，UNKNOWN 仍需核实。

## 6. 完成与后续

本地验收结果与具体提交保存在 PR；独立 AI Review 状态为 USER_WAIVED，不是 PASS。PR 合并后需在真实 main revision 重新验证受影响范围并安全清理本任务分支。项目复用路线图作为需求、PR 作为施工和证据载体，没有另建 Coding Change 或可关闭 Issue，相关归档/Issue Closure 不适用。

外部链路当前未验收：供应商原 PDF 与响应字段复核、真实站点权限/容量/并发/超时、可信网关、ADP 与企微 E2E。它们是生产启用门禁；取得环境后按既有编号补充证据，不把本地 Mock 结果改写为真实验收通过。
