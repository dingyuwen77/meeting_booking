# 会畅账号模式 MCP 改造：实施路线图与任务状态

## 1. 上游目标与范围

用户目标：企业微信员工通过腾讯 ADP 使用固定 MCP Server，基于会畅智云**账号模式**创建、修改和检查会议；复用企微 UserID 为会畅 userId；复用阶段一机器契约与 CLI；系统性治理中文编号技术文档；具备本地测试证据后按 Git PR 合并到 main。用户明确豁免本次**独立 AI Review**，其余测试、平台权限和 PR 门禁不豁免。

不做：物理办公室会议室 A301 自动预订、参会者自动邀请、已创建会议取消、直播/录制/纪要、生产 ADP 画布修改、真实生产数据操作及未获授权的 Release/Deploy。

## 2. 关键事实与设计比较

- 原仓库只有 JSON Schema、CLI、测试与路线图；没有 MCP、身份验证、会畅适配。
- 供应商提供的《会畅智云账号模式 Open API》v1.0.10：POST 使用 form，GMT，按用户 ID 和 APIKey + 毫秒时间戳 MD5 大写；同一 userId 预约不能时间重叠；confModify 不支持改时间，confModify2 支持时间/时长/方数。
- 企微 UserID 直接复用，避免另建用户映射；**用户标识不能代替身份认证**。
- 会畅虚拟 roomId 与企业实体会议室并不等价；不把 A301 映射为会畅 roomId。

真实方案取舍：
1. **直接把会畅 API 暴露给 ADP**：最省代码，但 LLM 可控制 provider 字段，难以安全统一身份/幂等/补参，故拒绝。
2. **保留独立公共 Schema + Domain + Provider**（推荐）：复用现有契约、标准化冲突与恢复，不把会畅细节泄露到 ADP；代价是增加少量业务模块与单机状态库。
3. **预建多 Provider、分布式数据库、消息队列**：当前只有会畅单系统与单实例需求，无相称证据，故不引入。

## 5. 分层门禁与当前状态

- **A：业务契约与会畅 OpenAPI 映射**——代码已编写，需真实 Schema/Unit 检查与 SDK/ADP 消费确认。
- **B：MCP 最小连通与身份探针**——服务代码已编写；真实 SDK v2/ADP 联调未验证。禁止假定 ADP 能透传动态可信 UserID。
- **C：Provider 真实操作**——代码已编写；无 siteSign/APIKey/隔离测试环境，真实查询/写入/并发仍未验证。
- **D：持久化多轮/未知状态**——SQLite 和 Fake 测试代码已编写；真实进程重启、超时及跨用户场景仍需运行验证。
- **E：完整企微/ADP E2E**——目标工作流不在本仓库；需在正式 ADP/企微租户联调后记录证据，当前不能称完成。

Acceptance 的完成状态只能从实际代码、测试输出、真实 Provider 结果和平台配置确定；不得因为此 Roadmap 有任务行或存在 Fake 测试文件而改成“已验证”。

## 6. 兼容、部署、回滚

阶段一 V1 尚未正式跨团队冻结，扩展 SUPPLY_FIELDS、确认会议摘要属于候选契约修订；既有 `SHIFT/PATCH` 未恢复。依赖新增 httpx 与官方 MCP SDK v2；不升级已有 jsonschema 约束范围。无 SQL Migration 资产；首次运行创建 SQLite 表，生产备份和迁移需单独执行。默认关闭写入，降级/回滚时仍需核实远端已发操作；撤回本服务版本不会取消会畅真实会议。
